# Database Migrations (Alembic)

The database schema is owned by **Alembic migrations**, not
`Base.metadata.create_all()`. Migrations are the single source of truth for the
schema and make changes reviewable, ordered, and reversible.

## Layout

```
alembic.ini                     # config (DB URL comes from app settings, not here)
alembic/
├── env.py                      # wires Base.metadata + the app's DATABASE_URL
├── script.py.mako              # migration template
└── versions/
    ├── f613530d17f9_initial_schema.py            # all 7 tables
    └── dc50846de5da_add_collected_at_*.py         # adds collected_at to epss/kev
```

`alembic/env.py` imports `backend.app.models` so every model is on
`Base.metadata`, and pulls the database URL from `get_settings()` — so there is
one source of truth for the connection (the `.env` file).

## Everyday commands

Run from the project root with the venv active:

```powershell
alembic current                 # show the DB's current revision
alembic history                 # list the migration chain
alembic upgrade head            # apply all pending migrations
alembic downgrade -1            # roll back the last migration
alembic revision --autogenerate -m "describe change"   # create a migration from model changes
```

## Application startup

On boot the API runs `alembic upgrade head` automatically (see
`backend/app/db_migrate.py`, invoked from the FastAPI lifespan). Disable this to
manage migrations manually:

```
AUTO_MIGRATE=false
```

## How Alembic was introduced to the existing database

The database already contained data when migrations were added, so:

1. The **initial migration** was autogenerated against a throwaway empty
   database, capturing all 7 tables exactly.
2. The live database was **stamped** at that revision
   (`alembic stamp head`) — marking it current *without* re-creating existing
   tables or touching data.
3. Subsequent changes (e.g. adding `collected_at`) are normal
   `alembic upgrade head` runs.

## Creating a new migration

1. Change the SQLAlchemy models under `backend/app/models/`.
2. `alembic revision --autogenerate -m "what changed"`.
3. Review the generated file in `alembic/versions/` (autogenerate is a starting
   point — check column types, server defaults, and data backfills).
4. `alembic upgrade head` to apply.

## Upgrade/downgrade validation

The initial migration was validated end-to-end on PostgreSQL: `upgrade head`
created all 7 tables, `downgrade base` removed them cleanly. The automated
suite (`tests/test_migrations.py`) additionally enforces a single linear head,
a complete chain to base, and that every model is registered for migration.

> Note: `collected_at` uses a Postgres `server_default` of `now()`, so the
> migrations target PostgreSQL (the platform's database). The unit tests
> deliberately do not run the migrations against SQLite.
